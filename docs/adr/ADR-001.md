# ADR-001: Capas simples para persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado: Aceptado — 2026-11-04

## Contexto
Tras integrar los patrones de comportamiento Chain of Responsibility (RF1), Strategy (RF2) y Observer (RF3) sobre el sistema de solicitudes de reembolso de gastos corporativos, corresponde decidir si el proyecto debe migrar hacia una Arquitectura Hexagonal completa (puertos e interfaces intermedias tanto para persistencia como para notificación) o si debe conservarse en una arquitectura en capas simples.

En el estado actual de la organización:
1. No existe ningún plan ni requerimiento de negocio para cambiar el motor de base de datos relacional (H2 en desarrollo / PostgreSQL en producción).
2. El área de Contabilidad anunció que durante el próximo trimestre integrará un sistema externo a través de una API REST para programar el desembolso de solicitudes aprobadas.

## Decisión
1. **Persistencia en capas simples:** Se mantiene una arquitectura en capas directa para la persistencia. `SolicitudReembolsoService` continuará dependiendo directamente de la interfaz `RepositorioSolicitudesJpa`, sin introducir una interfaz intermedia de puerto (`RepositorioSolicitudes`) ni adaptadores de repositorio con mappers de entidad. Un puerto de persistencia en este momento constituiría una abstracción puramente especulativa (*Speculative Generality* y violación de YAGNI), ya que no existe un segundo adaptador ni un caso de uso que lo justifique.
2. **Notificación desacoplada mediante Observer:** Para el módulo de notificación no se introduce ningún cambio estructural adicional. La interfaz `ObservadorCambioEstado` ya proporciona el *seam* (punto de costura) arquitectónico necesario. Cuando Contabilidad implemente su API externa el próximo trimestre, bastará con actualizar la clase `NotificadorContabilidad` para que invoque el cliente HTTP correspondiente, sin impactar en lo absoluto a `SolicitudReembolsoService` ni al resto de observadores (`NotificadorEmpleado`, `NotificadorAuditoria`).

## Consecuencias

### Positivas:
- **Simplicidad y mantenibilidad (KISS/YAGNI):** No se agregan interfaces superfluas ni mapeos manuales de objetos entre dominio y persistencia mientras exista un único motor de base de datos.
- **Preparación ante cambios conocidos:** El único cambio de infraestructura con fecha e intención confirmada (la integración de pagos de Contabilidad) ya cuenta con un punto de extensión desacoplado y listo para ser extendido.
- **Rapidez de desarrollo:** Menor fricción cognitiva al navegar la estructura del proyecto y menor cantidad de archivos boilerplate.

### Negativas:
- **Acoplamiento controlado a Spring Data:** Si en el futuro surgiera la necesidad imprevista de sustituir Spring Data JPA por una base de datos documental o un almacenamiento distribuido, la interfaz de puerto deberá introducirse de manera retroactiva; se asume conscientemente este costo en favor de la simplicidad actual.
- **Asimetría arquitectónica:** Un revisor que busque una arquitectura Hexagonal simétrica en todas las fronteras externas observará que la notificación sí posee inversión de dependencias mientras que la persistencia es directa; este ADR explicita y justifica dicha asimetría.
